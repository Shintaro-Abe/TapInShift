# クラウドキュー同期 要求定義

## 1. 目的

Windows 端末が停止している外出中でも、Slack App Home から TapInShift の出勤、退勤、メモ反映、日別編集を受け付けられるようにする。

クラウド側では Slack 操作を受け付けて最小限のイベントデータを保存し、Windows 端末の TapInShift Agent が起動後に未同期イベントを取得して、既存のローカル Excel 勤務表へ反映する。

## 2. 対象範囲

- Slack 受付を Socket Mode から HTTP Request URL 方式へ移行する。
- AWS Lambda Function URL で Slack からの HTTP リクエストを受ける。
- DynamoDB の単一テーブルに出退勤、メモ反映、日別編集、ユーザー設定を保存する。
- クラウド側で打刻時刻、丸め後時刻、任意メモ分類結果を確定する。
- Windows Agent が 5 分ごとにクラウド API をポーリングし、未同期イベントを Excel へ反映する。
- 手動同期コマンドで即時同期できるようにする。
- クラウド側で `queued -> claimed -> reflected/failed` の同期状態を管理する。
- Windows 側にもローカル SQLite 監査ログを残す。

## 3. 対象外

- Excel ファイルをクラウドへ保存すること。
- Excel パスワードをクラウドへ保存すること。
- Slack token をクラウド DB へ保存すること。
- クラウド上で Excel を直接編集すること。
- 複数ワークスペース、複数会社向けの SaaS 化。
- 勤務表フォーマットの変更。
- Excel 提出運用の廃止。

## 4. 前提

- 月額コスト最小を優先し、Render、Fly.io、Railway などの常時起動 PaaS ではなく AWS サーバーレス構成を採用する。
- Slack 受付は Lambda Function URL で受け、Slack 署名検証を Lambda 内で行う。
- Windows Agent からクラウド同期 API へアクセスする場合は専用 Bearer token を使う。
- クラウドには勤怠受付と同期に必要な最小限のデータだけ保存する。
- Excel ファイル、Excel パスワード、ローカル設定、ローカル SQLite は Git 管理対象に含めない。
- Windows Agent は自宅 PC またはローカル端末が起動している間だけ Excel 反映を行う。

## 5. ユーザーストーリー

### 5.1 外出中の出勤

ユーザーとして、Windows 端末をシャットダウンしていても、Slack App Home の出勤ボタンで出勤時刻を記録したい。

### 5.2 外出中の退勤

ユーザーとして、Windows 端末をシャットダウンしていても、Slack App Home の退勤ボタンで退勤時刻を記録したい。

### 5.3 外出中のメモ反映受付

ユーザーとして、勤務拠点、交通費経路、金額などの任意メモを外出中でも Slack から送信し、Windows 起動後に Excel へ反映したい。

### 5.4 外出中の日別編集受付

ユーザーとして、対象日を選んで出勤、退勤、届出内容、経費内容、金額を編集し、Windows 起動後に Excel へ反映したい。

### 5.5 起動後の自動同期

ユーザーとして、Windows 端末を起動したら、外出中に受け付けた未同期イベントが自動で Excel に反映されてほしい。

### 5.6 同期状態の確認

ユーザーとして、Slack App Home で少なくとも最新ステータス、未同期件数、直近の受付結果を確認したい。

## 6. 機能要件

- Slack App Home はクラウド側が生成する。
- App Home には出勤、退勤、任意メモ入力、メモ反映、日付選択、丸め単位選択を表示する。
- Slack の出勤/退勤操作を受けた時点で `tapped_at` を確定する。
- クラウド側で丸め処理を行い、`reflected_at` を確定する。
- 出勤は設定された出勤丸め方向、退勤は設定された退勤丸め方向を使う。
- 丸め単位設定は DynamoDB に保存し、以降の打刻に適用する。
- 任意メモ分類はクラウド側で実行し、分類結果を保存する。
- 日別編集は明示的な上書き操作として扱い、入力された項目だけ Excel へ反映する。
- 日別編集で空欄の項目は既存 Excel 値を保持する。
- 同日同種の出勤/退勤が既に存在する場合、クラウド側では受け付けるが Slack に警告を出す。
- Excel 反映時には既存セル上書き防止を維持する。
- Windows Agent は起動直後に 1 回同期し、その後 5 分ごとにポーリングする。
- 手動同期コマンドを用意する。
- `claimed` のまま一定時間更新されないイベントは、再同期対象へ戻せるようにする。
- Excel 反映に失敗した場合、失敗理由に応じて自動リトライ可否を分ける。

## 7. 非機能要件

- AWS の従量課金を前提に、常時起動サーバーを持たない。
- 低頻度の個人利用で月額コストが最小になる構成を優先する。
- Slack 署名検証に失敗したリクエストは処理しない。
- Windows Agent 同期 API は Bearer token なしでは処理しない。
- token、署名 secret、Excel password をログや DB に出力しない。
- クラウド DB には Excel ファイルや Excel password を保存しない。
- 同期処理は二重起動や途中停止に耐える。
- 既存の Excel 勤務表運用を壊さない。

## 8. 受け入れ条件

- Windows Agent が停止していても、Slack App Home で出勤、退勤、メモ反映、日別編集を受け付けられる。
- 受付済みイベントが DynamoDB に `queued` として保存される。
- 出勤/退勤イベントには `tapped_at` と `reflected_at` が保存される。
- 任意メモイベントには生メモと分類結果が保存される。
- 日別編集イベントには対象日と入力された項目が保存され、空欄項目は既存値保持として扱われる。
- Windows Agent 起動後、未同期イベントを claim して Excel へ反映できる。
- 反映成功時にクラウド側が `reflected` へ更新される。
- 反映失敗時にクラウド側が `failed` または再試行対象状態へ更新される。
- ローカル SQLite に Excel 反映試行の履歴が残る。
- Slack App Home に最新ステータスと未同期件数が表示される。
- 秘密情報、Excel ファイル、ローカル SQLite が Git 管理対象に含まれない。

## 9. 制約

- クラウド側は Excel の現物を参照できないため、Excel 既存セルとの完全な事前整合性チェックは行わない。
- 最終的な Excel 上書き防止は Windows Agent の Excel 反映時にも行う。
- Slack UI の詳細履歴表示、失敗一覧、再同期ボタンは初期範囲に含めない。
- 実装は段階移行とし、既存ローカル方式を即時削除しない。
